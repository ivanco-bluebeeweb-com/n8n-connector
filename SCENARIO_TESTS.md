# Scenario Tests (PST) — n8n Connector

Метод: `Docs/session-notes/SCENARIO_TESTING_STANDARD.md`. Этот файл — обязательный
журнал прогонов Plausible Scenario Testing для этого приложения, дополняющий
(не заменяющий) `POST_AUDIT_LOG.md`: пост-аудит сверяет статическую
согласованность кода (manifest↔schemas↔handler↔client), PST реально
**вызывает** код через `imperal_sdk.testing.MockContext` и ловит то, что
статическая сверка структурно не видит (неверное число позиционных
аргументов при вызове, несуществующие kwargs SDK, некорректное
восстановление после ошибок, двойные вызовы деструктивных операций).

---

## Прогон 2026-08-19

**Почему через MockContext, а не через живой n8n-инстанс.** У пользователя
нет подключённого BYOK n8n-инстанса (`get_n8n_connection` → `connected:
false`). Поднять настоящий n8n локально не удалось: Docker недоступен в
этом окружении, а `npx n8n` не устанавливается за разумное время (тяжёлый
npm-пакет). Следующий по строгости честный вариант — реальные вызовы
`handlers.py`/`n8n_client.py` (тот же код, что исполняется в продакшене)
через официальный `imperal_sdk.testing.MockContext` + `MockHTTP`,
подставляя контролируемые ответы, соответствующие реальному REST-контракту
n8n (задокументированному и подтверждённому в `PREPARATION.md` §2 против
docs.n8n.io). Это не имитация логики — код приложения исполняется
по-настоящему, только сетевой транспорт — тестовый двойник вместо чужого
живого сервера.

**Персона.** У n8n Connector функционально одна роль: BYOK-владелец
собственного n8n-инстанса с API-ключом ("Marina", agency ops lead, см.
PREPARATION.md §1). Разнообразие сценариев здесь идёт не от множества
персон, а от классов данных инстанса: пустой/типичный/пограничный/
невалидный/экзотический (self-hosted Community vs Cloud/Enterprise со
scopes, старые версии n8n без `/execute`, повторные операции).

**Харнесс:** `tests/conftest.py` (`ctx`, `ctx_connected` fixtures — зеркалит
принятый в репозитории паттерн DataForSEO Connector / Media Studio),
`tests/test_pst_scenarios.py` — 27 тестов, реальные вызовы `handlers.py`.

**Покрытие по 5 обязательным веткам:**

1. **Happy path** — connect (сохраняет креды), list/get/create workflow,
   run workflow, list executions/credentials/tags/variables/users на
   типичном и на пустом инстансе.
2. **Error** — 401 (неверный ключ/URL, креды НЕ сохраняются), 403
   (ключ распознан, но не хватает scope — отдельная, более специфичная
   ошибка), 500 (внутренняя ошибка n8n), 404 на `/execute` (старая версия
   n8n без этого эндпоинта — сообщение должно отличать это от общей
   ошибки).
3. **Blocked** — каждая из 11 репрезентативных функций (по одной на
   ресурс: workflows/executions/credentials/tags/variables/users/audit)
   корректно возвращает "не подключено", когда credentials отсутствуют —
   параметризованный тест на всё дерево ресурсов, не только на одну
   функцию.
4. **Recovery** — create_workflow: первый вызов ловит 500, второй
   (тот же payload) после восстановления backend успешно проходит без
   остаточного состояния от неудачной попытки.
5. **Adversarial** — двойной delete_workflow подряд (soap-opera класс):
   первый вызов удаляет по-настоящему, второй должен НЕ повторно
   заявлять `deleted: true` без реального эффекта.

**Пустой инстанс:** list_workflows на только что созданном инстансе без
единой workflow — пустой список, без ошибок пагинации.

### Найденные и исправленные баги (не пойманы предыдущим статическим
### пост-аудитом от 2026-08-19 — см. `POST_AUDIT_LOG.md`)

1. **`update_n8n_variable` — неверное число позиционных аргументов.**
   `handlers.py` вызывал `nc.update_variable(ctx, base_url, api_key,
   params.variable_id, params.value)` — 5 аргументов на сигнатуру, которая
   требует `(ctx, base_url, api_key, variable_id, key, value,
   project_id="")`. `params.value` попадал на место `key`, а обязательный
   `value` не передавался вовсе — гарантированный `TypeError` при первом
   же реальном вызове update. Найдено чтением кода перед написанием теста,
   подтверждено автоматической AST-сверкой всех вызовов `nc.*` в
   `handlers.py` против сигнатур в `n8n_client.py` (больше несовпадений не
   нашлось). **Исправлено:** передаются все требуемые аргументы, включая
   `params.key` и `params.project_id`.

2. **`run_n8n_workflow` и `get_n8n_execution` — несуществующий kwarg
   `data_extra` у `ActionResult.success()`.** Реальный SDK
   (`imperal_sdk.types.action_result.ActionResult.success`) принимает
   только `data, summary, *, ui, refresh_panels` — параметра `data_extra`
   не существует. Оба вызова гарантированно роняли `TypeError` при каждом
   реальном использовании — `run_n8n_workflow` (самая частая операция
   "запустить workflow") и `get_n8n_execution` с `include_data=True`.
   Найдено прогоном happy-path теста (реальный `TypeError`, не
   предположение). **Исправлено:** данные вложены в уже объявленные поля
   моделей — `execution_id` в `WorkflowActionResult`, новое поле
   `run_data: dict` в `N8nExecution` (заполняется только когда
   `include_data=True`).

## Прогон 2026-08-20 — Часть D (Deploy Verification / Idempotency / Security-SSRF / Regression grep)

**D1 (Deploy Verification):** не применялось — код приложения не менялся в этой части (только тесты).

**D2 (Idempotency):** уже покрыто существующим adversarial-тестом прогона 2026-08-19 (`test_delete_workflow_twice_second_call_is_not_found`) — повторный `delete_n8n_workflow` на уже удалённом workflow получает чистый not-found, не ложный повторный успех. Новых D2-тестов не добавлялось.

**D3 (Security/SSRF) — сознательно НЕ применяется как уязвимость к этому приложению.** n8n Connector — BYOK-коннектор: весь смысл приложения — обращаться к СОБСТВЕННОМУ n8n-инстансу пользователя по адресу, который пользователь сам сохранил (`base_url`). «Отказывать на приватном/внутреннем адресе» здесь сломало бы реальное предназначение — многие self-hosted n8n-инстансы легитимно живут в приватной сети/VPN, к которой у инфраструктуры пользователя есть доступ. Вместо этого D3 переопределён для этого класса приложений как: каждый исходящий вызов должен строиться ИЗ сохранённого `base_url`, никогда не из хардкода или иного источника — регрессия здесь означала бы тихое обращение не к тому n8n.

**D4 (Regression grep):** добавлен `test_d4_every_outbound_call_is_built_from_the_stored_base_url` — грепает `n8n_client.py` на каждый `ctx.http.*` вызов и подтверждает, что URL рядом строится через `_api(base_url, ...)`. Самопроверка: первая версия теста была слишком грубой (искала `base_url` в ТОЙ ЖЕ строке текста, что и сам вызов) и падала на многострочных вызовах, где `_api(base_url, ...)` идёт на следующей строке — не баг приложения, а слишком строгая логика собственного теста; исправлено проверкой окна из нескольких строк после каждого вызова.

**Итог:** 28/28 тестов зелёные (было 27). Реальных багов в этой части не найдено.
