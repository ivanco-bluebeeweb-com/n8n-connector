## 2026-08-19 — первичное выставление цен (per_action), 48 функций

**Контекст:** после завершения Среза 3 (полное покрытие n8n Public API) и
обязательного сквозного функционального пост-аудита (задача #1915,
раздел "Сквозной пост-аудит" — манифест ↔ схемы ↔ handlers ↔ клиент
сверены на 100% из 48 функций через `_audit.py`, 2 найденных бага
исправлены и задеплоены), приложение готово к выставлению цен как
последний шаг перед публикацией в Marketplace.

**Модель:** `per_action` — цена за вызов, а не подписка. Обоснование: n8n
Connector — BYO-инстанс коннектор (пользователь сам хостит/платит за свой
n8n, self-hosted или Cloud), поэтому наша ценность — удобный доступ к API
из чата/панели, а не инфраструктурные расходы на сам вызов; плоская
подписка не отражала бы то, что кто-то дергает 2 функции в месяц, а
кто-то — 200.

**Обязательная фиксированная платформенная шкала:** `{0, 8, 16, 20, 40, 60}`
(закреплена по итогам исправления Make.com Connector — см. его собственный
`PRICING_HISTORY.md` — как ОБЯЗАТЕЛЬНАЯ для каждого приложения на
платформе, не самодельная шкала под конкретное приложение). Все 48/48
функций n8n Connector явно оценены на этой шкале — ни одна не оставлена на
платформенных дефолтах.

**Полная таблица (48/48 функций с ценой)** — источник истины:
`tool-prices.json` в корне приложения, зеркалированный в
`imperal.json["pricing"]["tool_prices"]`.

**Метод применения (по образцу WordPress Hub / Make.com Connector):**
1. Создан `tool-prices.json` в корне приложения — единственный источник
   истины для цен.
2. `imperal.json` получил блок `pricing` (`model`, `currency`,
   `monthly_price`, `free_tools`, `tool_prices`, `notes`) — идентичной
   структуры файлам WordPress Hub и Make.com Connector.
3. Реальное применение на платформе — через `developer.save_pricing`
   (не `update_pricing` — см. известное ограничение платформы ниже).

**Известное ограничение платформы (не наша ошибка, зафиксировано ранее в
работе над Make.com Connector, Imperal Cloud task #1663, пункт #17):**
`developer.update_pricing` консистентно возвращает ошибку валидации типа
параметра независимо от формата `pricing_config`; `developer.save_pricing`
проходит без ошибки, но ни один read-инструмент (`get_app_details`,
`apps_by_developer`) не показывает реально сохранённый `tool_prices` даже
у уже опубликованного приложения. Итоговое подтверждение цены возможно
ТОЛЬКО через панель Imperal (Developer → My Apps → n8n → Pricing).

**Tier/split на момент записи:** developer tier = `explorer` (70/30
split, no payout yet). Не влияет на цену, которую видит пользователь,
только на долю разработчика.

**Кто принял решение:** Webbee, по прямому поручению пользователя
(vlad@bluebeeweb.com) — "выставь прайсинг приложению" — как обязательный
шаг ПОСЛЕ завершения функционального пост-аудита (см. #1915), применённый
по уже закреплённой на платформе фиксированной шкале {0,8,16,20,40,60}.

**Следующий пересмотр:** при следующем изменении набора функций
(добавление/удаление tool'а, например Projects API если появится запрос)
или по итогам первых реальных данных об использовании (earnings/action_count
через `get_earnings_by_app`) — тогда здесь появится новая датированная
запись с обоснованием, что именно изменилось и почему.
